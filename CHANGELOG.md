## [Unreleased]

### Added
- Team mode, first stage (design: `docs/design/team-mode.md`). When `.sancho/team.json` exists, several people share a project from their own clones: each member is recognized by `git config user.email` (or `SANCHO_USER`); task states are appended to a per-member event log, `.sancho/log/<member>.jsonl`, so merging the members' work never conflicts on Sancho's state (`.gitattributes` gets `merge=union` for a member working from two computers); the current state is the backlog plus every event. New `state.py` commands: `team add|list|suggest`, `whoami`, `claim` and `release` (one task, one person; a contested claim goes to the earliest and the other member is told), `review --approve|--changes` (qa role, four eyes: not by whoever worked on the task). `next` answers for the member who asks, `next --team` gives one line per member, `status` shows who holds what, conflicts and stale claims. New schemas `team` and `event`, optional `task.assignee`, rules for the model in `references/team.md`. Without `team.json` nothing changes. Checks: `team_merges_without_conflicts` (three people, four clones, merged in turn), `team_contested_claim`, `team_four_eyes_and_review`, `solo_mode_unchanged_with_task_command`.
- Team mode, second stage: gates and VERIFY. The coordinator starts and submits phases; `team.json` names gate `approvers` and a `quorum` per phase, each approver approves in their own session (`gate_approve` events), the gate closes when the quorum is reached and records `approved_by`; one rejection sends it back. Decisions and approvals record the member's id. Testers claim UAT cases and record results with `state.py uat`, developers claim defects and mark them `fixed`, another qa member marks them `verified` (four eyes), `wont_fix` is the coordinator's. Two members opening the same defect id: the later one is renamed. `next` in VERIFY gives each member their own case, defect or verification. `state.py compact` (coordinator) moves the events of settled items into `backlog.json`/`uat.json` and `.sancho/log/archive/`, checking that the state is unchanged. Checks: `team_gate_quorum`, `team_verify_and_compact`.
- Team mode, third stage: `state.py since [REF] [--json] [--peek]` lists what the others did since you last looked (their commits, events, phase changes and documents; what concerns you first; your own work left out), with a personal marker in the git folder. `state.py hooks install|remove|status` adds a `post-merge` hook that prints it and validates the files after every pull. `state.py renumber [--apply]` renames duplicate ids created in parallel and lists the references to check. Checks: `team_since_and_hook` (a real pull runs the hook), `renumber_duplicate_ids`.
- Team mode, fourth stage: the plugin panel shows **Squadra** (who you are, what each member holds, contested and stale claims, renamed defects, gate votes) and **Novità** (what the others did since you last looked, what concerns you first, **Segna come viste**); the band shows a "novità per te" badge and a notice appears when something new concerns you. Usage guide chapter 11 "Working as a team" and a README section in English, Italian and Spanish; four behavioral evals (`team`). Panel test: `team mode: squad, news for you, mark as seen`.
- `state.py uat` and `state.py defect` also work for one person, writing `uat.json` through the schema instead of hand edits.
- `state.py task TASK --status ... [--evidence TYPE:VALUE]`: task status changes through a validated command, also for one person, instead of editing `backlog.json` by hand.

## [1.0.0] - 2026-11-12

First public release.

### Added
- Sancho skill: eight gated phases (DISCOVER, SPECIFY, PLAN, TASKS, IMPLEMENT, VERIFY, RELEASE, EVOLVE) with `help`, `status`, `next` and `checkpoint` commands.
- Seven roles (Analyst/PM, UX/UI designer, Architect, Developer, QA, Security, Release manager), shipped as Claude Code subagents through the plugin.
- Claude Code plugin and marketplace manifests, thirteen slash commands.
- JSON schemas: state, backlog, UAT, handoff (adapted from ACP v1.1), security report.
- Scripts (Python standard library): `state.py`, `coherence_check.py`, `complexity.py`, `uat_export.py`, `cve_enrich.py` (OSV, NVD, CISA KEV, FIRST EPSS, offline-safe), `contrast_check.py`.
- Gate checklists, phase references, templates (constitution, spec, plan, ADR, threat model, security report, retrospective, checkpoint, glossary, standard).
- FieldLog end-to-end example, 37 offline self-tests, 23 behavioral evals, installation and usage guides in English, Italian and Spanish.
- Sancho panel in the plugin (`hooks/`, `types/`), for the Claude app (Code tab) and Claude Code: a band above the prompt (phase and gate, blockers, next step), a notice when the gate, the next step or the ZIP state changes, and a details pane opened from the band or with `/sancho-panel` (phase stepper, next step, defects and security findings by severity, tasks and UAT, command buttons that fill the prompt). Read-only: it runs the bundled `state.py status --json`; in a repository checkout it also compares `dist/sancho.zip` with `skills/sancho`. Not in the ZIP for the Claude apps, which cannot show it. Tests: `claude plugin test .` (10) and check `panel_wired`.
- `assess` command (`references/assess.md`, `templates/assessment.md`, plugin command `/sancho:assess`): read-only analysis of an existing project. Maps stack and history, reads the core, checks secrets in git, dependencies (`cve_enrich.py`, other lockfiles listed as NOT RUN), security by reading, analyzer and tests when they run locally; blocker and major findings go first under "Act first", secret values are never printed, every claim has an evidence label; closes with a roadmap, a reuse list or go/no-go, and offers to continue with `discover`. Added after two real analyses ran outside any Sancho procedure. Refined after a trial run on a real project: `cve_enrich.py --no-nvd` by default with output outside the project, secrets searched by names only, tests run only when isolated from real databases, working tree analyzed, dependency findings summarized one row per package, the answer to the question right after "Act first". Docs in EN/IT/ES, eval 23. Check: `assess_command_wired`.

### Changed since the internal build of 2026-10-28
- Both invocation forms are now explicit in `SKILL.md`, `references/commands.md`, the guides and the READMEs in English, Italian and Spanish: `/sancho:<command>` in Claude Code with the plugin, `/sancho <command>` (with a space) in the Claude apps and in Claude Code with the skill only. Sancho ignores a leading colon in the arguments (`/sancho :status`) and suggests commands in the form of the current environment. Check: `invocation_forms_documented`.
- Rules clarified after running the behavioral evals (check: `references_cover_eval_gaps`): `help uat` names both ways of running UAT; L0 DISCOVER asks at most three questions, with level and stack as defaults; a question about both status and next step ends with one NEXT step; the first-run tour is skipped when the first message already describes a project; `status` checks the core files, handoffs stay with `validate`.
- Sancho now replies in the language of the user's latest message; a bare command keeps the language of the conversation so far, and `settings.language` applies only when there is none. Before, the setting won and English users of an Italian project got Italian replies. Check: `references_cover_eval_gaps`.
- UAT cases were written in English for Italian testers, because internal files stay in English. Text for testers and end users (UAT cases, release notes) now uses the project language, `settings.language`; ids and keys stay in English, and the UAT export uses the project language unless the user asks otherwise. Check: `references_cover_eval_gaps`.
- From the user's runs in the desktop app (2026-11-09), check `status_relay_rules`: `status` relays only the script output, keeps one layout in every language and ends with exactly one NEXT line (it had added case tables and lists of actions); with no project it says so in one line and offers DISCOVER instead of showing the tour; a new UAT case is written in the project language even when the existing cases are in another language (it had copied their English).
- Active security tests on the user's own production were always refused. Decision of 2026-11-09: they are allowed only with an explicit approval of target, scope and an agreed time window, recorded with the new `state.py approval --window START/END`; Sancho explains the risks first, recommends staging, runs only inside the window and stops at the first sign of degradation. Third-party targets are still always refused. Docs updated in EN/IT/ES. Check: `production_testing_needs_window`.
- `status` still drifted in the desktop app after the wording fix (a major shown as a blocker, lines after NEXT). `commands.md` now gives a template to copy: one code block, fixed lines, Blockers only from the script's BLOCKER lines ("none" otherwise), nothing after the Next line. Check: `status_relay_rules`.
- `state.py next` in VERIFY named the first open major defect even when a blocker was open: a security finding raised to blocker, or a blocker defect listed after a major. Blockers now come first (blocker defects, then unresolved security blockers, then major defects). Check: `next_puts_blockers_first`.

### Fixed since the internal build of 2026-10-28
- `state.py status` counted every security finding by severity, including fixed ones, because it printed the report summary (FieldLog showed "major 2" with only F-001 open). It now counts unresolved findings (`open`, `not_verified`) from the findings list, lists closed ones by status (`fixed`, `accepted_risk`, `false_positive`) and keeps the NOT RUN count; `status --json` gains `security.closed`. Regression test: `status_counts_only_open_security_findings`.
- `state.py status` listed only `open` security findings among the BLOCKER lines; a blocker finding still `not_verified` is now listed too, consistent with the counts. Regression test: `status_lists_unverified_security_blockers`.
- `state.py status` showed a partial status as if it were complete when a project file was invalid: a `uat.json` without `cases` just lost its UAT line and exited 0, and a case without `result` or a file that was not JSON ended in a traceback. `status` now validates the files itself, prints an `INVALID:` line per file, leaves out that file's counts and exits 1; `status --json` gains `invalid_files`. `status` and `next` replace the next step with the repair step, because it cannot be worked out from invalid data. `validate` reports a file that is not JSON as `FAIL` instead of crashing, and an unreadable `state.json` is a clear error. Regression test: `status_reports_invalid_files`.
- `cve_enrich.py` created one finding per OSV advisory, so an issue published as both GHSA and PYSEC was counted twice (23 findings for 18 issues on the test inputs, seen only against the real APIs). Advisories of the same issue on the same package now become one finding, with the most severe rating; the others are named in `severity_rationale`. Regression test: `cve_aliases_are_one_finding`.
- `cve_enrich.py` stopped with no report on a missing input, so a project with no lockfile had nothing to show. The input is now listed in `summary.not_run`, the report is written and the exit code stays 2. Regression test: `cve_missing_input_is_reported`.
- `state.py start` on a phase already in progress overwrote `started_at`, and every phase command runs `start`. Regression test: `start_keeps_the_original_start_date`.
- `state.py next` after a rejected gate only said to rework the phase; it now keeps the concrete step, for example the defect to fix. Regression test: `next_after_reject_names_the_concrete_step`.
